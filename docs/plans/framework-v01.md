# Slidock フレームワーク v0.1 詳細設計

## 導入・設定・CLI

### 1. 目的とアーキテクチャの境界

#### 1.1 目的と背景課題
Slidock は、複数の Slidev スライドプロジェクトを統合して互換性のある共有バンドルを生成し、柔軟にカスタマイズ可能な Web フロントエンド API を提供するフレームワークである。バージョン 0.1 では、利用者がローカル環境で自身の Markdown スライド群を簡潔に管理・閲覧・配信できる基盤を整えることを主目的に据えている。

従来の構成では、高度なリモート配信や専用の同期プロトコルを担う CLI ツールとフレームワーク本体の役割分担が複雑化し、ローカルでの手軽なスライド統合を目的とする利用者に対しても不要な学習コストや重厚な依存関係を強いる課題があった。そこで v0.1 では、単一の公開エントリパッケージである `@slidock/slidock` を導入するだけで、スライド群の構成定義からローカルでの開発、静的ビルド、プレビューまでの一連のライフサイクルを完結できる構成へと再編する。

#### 1.2 パッケージ境界と依存関係の整理
利用者の導入容易性と保守性を両立するため、フレームワーク本体と周辺ツールの境界を以下のように明確化する。

- **公開エントリの一元化**: 新規の利用者は `@slidock/slidock` のみをインストールし、手元の Markdown ファイル群を用意して作業を進める。メインパッケージ自体がローカルライフサイクルを操作するコマンドライン実行ファイル（bin）を提供する。
- **リモート向け CLI との分離**: 既存の `@slidock/cli` は、Slive プロトコルや高度なリモート公開を担う専用ツールとして存続させる。フレームワーク側から CLI への依存は一切持たせず、循環依存を排除する。既存の `buildHub` や `devHub` などのコア API は変更なくそのままエクスポートし、後方互換性を保ちながら新規のプロジェクト向け API を追加する。
- **軽量な既定値の適用**: 新規の利用パスでは、インストール時や初期起動時における Chromium の自動ダウンロードやオフライン用アセットの事前取得を行わない軽量構成を既定とする。一方、従来の `buildHub` を直接呼び出す既存パイプラインの動作を破壊しないよう、レガシー API においては `offline: true` および `thumbnails: 'auto'` という従来の既定値をそのまま維持する。
- **ブラウザランタイムの独立性**: ブラウザ環境専用の API 群には Node.js の組み込みモジュールや Node.js 固有の依存関係を含めない（Node-free）。フロントエンドの実装方針としては Vue ファーストを維持し、表示スロットやヘッドレスクライアントの柔軟性を保持する。
- **v0.1 の機能境界**: 本バージョンでは、コンテンツ管理（CMS）やデータベース管理用の管理画面、汎用的なプラグインフレームワーク、および新規の埋め込みコントローラは実装範囲に含めない。既存のネイティブ機能やリモート公開機能は任意のオプションとして維持される。

#### 1.3 動作環境・配信条件・ライセンス
Slidock の実行基盤および配信要件は以下の通りである。

- **Node.js 実行環境**: プロジェクトの基準バージョンとして `Node.js >= 24.15.0` を要求する。TypeScript 設定の読み込みなどに Node.js 24 が備える機能を利用することで、開発環境の構成を簡素化する。
- **検証済みプラットフォーム**: 現時点で初期計測および動作検証が完了しているオペレーティングシステムは Linux のみである。macOS および Windows での動作については、実際の CI 環境でテストが実行・確認されるまでは未検証として扱う。
- **静的ホスティングとベースパス**: Web サーバのルートパス（`/`）への静的配置を正式にサポートし、動作検証を実施している。新しい設定形式においてはルートパスのみを受け付け、ルート以外のパス接頭辞（例: `/docs/` など）を指定した場合は利用者が修正可能な設定エラー（actionable CONFIG error）として明示的に拒絶する。未検証のベースパス設定を許容して動作可能と誤認させることを防ぎ、利用者が直面する配信トラブルを未然に防止する。
- **ライセンスの遵守**: リポジトリのルートに MIT ライセンス（LICENSE）を配置する。第三者製コードやサンプルコードの既存ライセンスについても適切に維持・継承する。
- **開発・公開フェーズの制約**: 実装作業の期間中は、npm レジストリへの公開、リモートリポジトリへの push、および外部へのデプロイは行わず、レビュー可能なアルファ版の成果物を準備することに専念する。

### 2. プロジェクト設定 API

#### 2.1 設定ファイルの探索と読み込み機構
プロジェクトの設定は `packages/slidock/src/node/project.ts` に集約され、設定定義ヘルパーである `defineConfig` および設定読み込みを行う `loadProject` を通じて処理される。

```typescript
export function defineConfig<const T extends SlidockConfig>(config: T): T {
  return config;
}

export async function loadProject(options?: {
  root?: string;
  config?: string;
}): Promise<{
  root: string;
  configPath?: string;
  options: HubBuildOptions;
}>;
```

`defineConfig` は実行時には渡された設定オブジェクトをそのまま返す恒等関数として動作し、エディタ上での TypeScript 型推論と入力補完を支援する。

`loadProject` は以下の手順と規則に従って設定を読み込む。

1. **基準ディレクトリの決定**: プロジェクトのルートディレクトリ（`root`）は、明示的な指定がない限り実行時の作業ディレクトリ（`process.cwd()`）を採用する。
2. **設定ファイルの探索優先順位**: 設定ファイルの明示的なパスが指定された場合は、`root` からの相対パスとして解決する。明示的な指定がない場合は、`root` 直下から以下の順序で探索を行い、最初に発見されたファイルを採用する。
   - `slidock.config.ts`
   - `slidock.config.mjs`
   - `slidock.config.js`
   - `slidock.config.json`
   - `hub.config.json`
   採用された設定ファイルは、後続の処理やログ出力のために呼び出し元へ報告される。
3. **TypeScript の評価**: `slidock.config.ts` の読み込みには、Node.js 24 の型除去（type stripping）機能およびネイティブなモジュールインポートを利用する。これにより、設定ファイルを解釈するためだけに重厚なバンドラ依存関係や外部のトランスパイラを追加する必要をなくしている。
4. **エクスポート形式の制約**: JavaScript および TypeScript の設定ファイルでは、設定オブジェクトをデフォルトエクスポート（default export）として記述する必要がある。初期化処理の決定性を保ち、起動時の不要な非同期の複雑さを排除するため、非同期ファクトリ関数（async factory）による設定返却はサポートしない。
5. **JSON 設定のスキーマ要件**: JSON 形式で設定を記述する場合、新しい命名規則（`slidock.config.json`）では `schemaVersion: 1` の指定は任意（省略可能）である。一方、従来の `hub.config.json` を使用する場合は、後方互換性を維持するために既存のスキーマ定義が必須となる。
6. **相対パスの解決基準**: 設定ファイル内に記載される相対パスは、設定ファイル自身が存在するディレクトリを基準として解決する。
7. **信頼モデル**: 設定ファイルのインポート処理は、ローカル環境の信頼されたコードを実行する前提で動作する。
8. **キャッシュ制御**: 設定の再インポートを行う際は、古いモジュールキャッシュを参照しないよう制御してインポートを行う。ただし、設定ファイルから読み込まれる補助モジュール全体のホットモジュール置換（HMR）までは保証しない。
9. **未知プロパティの拒絶**: 設定オブジェクトに定義外のプロパティが含まれていた場合、設定の記述ミスや古い仕様による予期せぬ動作を防ぐため、エラーを出力して設定を拒絶する。

#### 2.2 設定スキーマ（SlidockConfig）と既定値
`SlidockConfig` は、従来の `HubBuildOptions` から実行時コールバックや内部パス（`configPath`, `baseDir`）を除外した安全な宣言的インターフェースとして定義され、配備先ベースパスとして `basePath?: '/'` を受け付ける。

| 設定項目 | 型 | 既定値 | 説明 |
| :--- | :--- | :--- | :--- |
| `sourceRoot` | `string` | `'./slides'` | Markdown スライドを探索する基点ディレクトリ。 |
| `outDir` | `string` | `'./dist'` | 静的成果物の出力先ディレクトリ。 |
| `include` | `string[]` | `['**/slides.md']` | スライドとして取り込む対象ファイルのグロブパターン。 |
| `offline` | `boolean` | `false` | オフライン用アセットの事前ダウンロードを制御する。 |
| `thumbnails` | `'auto' \| 'none'` | `'none'` | スライドサムネイルの生成方式。初期起動を高速化するため既定では無効。 |
| `compatibilityGroups` | `boolean` | `true` | Slidev のバージョン、テーマ、セットアップ、コンパイル設定等に基づく互換性グループ化を有効にする。 |
| `allowEmpty` | `boolean` | `true` | スライドが存在しない場合でもビルド失敗とせず空の状態で完了を許可する。 |
| `basePath` | `'/'` | `'/'` | 配備先のベースパス。現状は `'/'` のみが有効。 |

新規設定では軽量性と即時性を重視し、オフラインダウンロードを無効（`offline: false`）、サムネイル生成を無効（`thumbnails: 'none'`）としている。これに対して、レガシーな `hub.config.json` を用いた運用では、既存プロジェクトの挙動を意図せず変更しないよう、従来の既定値および広範な Markdown 探索ロジックがそのまま適用される。

テーマの指定においては、設定されたパッケージテーマ名をまず利用者のプロジェクト環境から解決を試み、見つからない場合はツールチェーン側から解決する。明示的な相対パスや絶対パスによるテーマファイルの指定もサポートされている。指定が省略された場合の既定テーマには `@slidev/theme-default` が適用される。

### 3. コマンドラインインターフェース

#### 3.1 CLI のアーキテクチャと実行方式
CLI の主要なロジックは `packages/slidock/src/node/project-cli.ts` に配置される `runProjectCli` 関数に実装され、実行バイナリである `node/bin/slidock.ts` は引数をそのまま受け渡して委譲する。

```typescript
export async function runProjectCli(
  args: string[],
  cwd?: string
): Promise<void>;
```

この分離により、CLI のプライベートな内部モジュールを外部へ漏洩させることなく、クリーンな委譲関係を実現している。また、既存の `@slidock/cli` に対しても、この委譲構造を通じて `create`, `dev`, `preview` の各コマンドが追加される。既存の CLI 環境では、新しい設定ファイルが存在するか、あるいはレガシー設定が存在しない場合にのみ新設計の `build` および `check` が呼び出され、従来のフラグやリモート公開用コマンド、および従来のリモート初期化（init）の挙動は変更せず維持される。

#### 3.2 サブコマンドの仕様
提供されるサブコマンドおよびオプションは以下の通りである。

- `create [directory]`
  新規プロジェクトの雛形を生成する。対象ディレクトリの指定を省略した場合は現在のディレクトリ（`.`）を対象とする。
- `dev [--config PATH] [--port 4174]`
  ローカル開発サーバを起動する。`--port` は 0 から 65535 までの整数値を受け付ける。開発時の安全性を考慮し、バインド先はループバックアドレス（`127.0.0.1` または `localhost`）に制限される。
- `build [--config PATH]`
  設定内容に基づいて Markdown スライド群を解析し、静的配信用の成果物を `outDir` へ出力する。
- `preview [--config PATH] [--port 4174] [--host 127.0.0.1]`
  ビルド済みの静的成果物をローカルで確認するためのプレビューサーバを起動する。このコマンドは設定で指定された出力ディレクトリ（`outDir`）の成果物のみを参照して動作し、ビルド後にソースファイルが存在しない状態であっても正常に機能しなければならない。スライドの再正規化処理やソースファイルの存在確認を前提としてはならない。
- `check [--config PATH]`
  設定ファイルの構文やスライドの参照関係を検証し、潜在的なエラーを静的に診断する。
- 共通オプション:
  - `--help`, `-h`: ヘルプ情報の表示。
  - `--version`: バージョン番号の表示。
  - `--json`: 出力を機械可読な単一の JSON 形式に統一する。

#### 3.3 プロセス制御と入出力契約
CLI は自動化ツールや外部スクリプトとの親和性を高めるため、明確な出力規約と終了ステータスを備えている。

- **診断メッセージの分離**: 人間向けの対話メッセージ、警告、エラー診断はすべて標準エラー出力（stderr）へ出力する。
- **JSON エンベロープ**: `--json` フラグが指定された場合、標準出力（stdout）には必ず単一の JSON オブジェクト（エンベロープ）を出力する。
  - 成功時:
    ```json
    {
      "ok": true,
      "command": "slidock build",
      "result": {
        "output": "/tmp/site",
        "deckCount": 2,
        "groups": []
      }
    }
    ```
  - 失敗時:
    ```json
    {
      "ok": false,
      "command": "slidock build",
      "error": {
        "code": "CONFIG",
        "message": "Only root basePath '/' is accepted."
      }
    }
    ```
- **終了コード（Exit Codes）**:
  - `0`: 正常終了。
  - `1`: 実行時エラー（ビルド失敗、接続エラーなど）。
  - `2`: 入力エラー（不正な引数指定、設定構文エラーなど）。
- **長時間稼働プロセスのライフサイクル**: `dev` や `preview` などの長時間稼働コマンドは、サーバの起動とリッスンが完了した段階で一度だけ準備完了（readiness）を示すエンベロープを発行する。その後は `SIGINT` または `SIGTERM` を受信するまで待機状態を維持し、シグナルを受信した際にはすべての子プロセス、リッスンポート、およびファイル監視リスナーを確実にクローズしてから安全に終了する。

#### 3.4 雛形生成（create コマンド）の安全設計
`create` コマンドは、初心者が迷わずにプロジェクトを開始できるように最小限かつ実用的なファイル群を展開する。同時に、既存の作業環境を意図せず破壊しないよう厳密な安全策が講じられている。

1. **生成される構成資産**:
   - `slidock.config.ts`: `@slidock/slidock` から `defineConfig` をインポートし、ホームタイトル（home title）、サンプルのメタデータ、および標準の既定値を定義した設定ファイル。
   - `slides/welcome/slides.md`: 最小限の初期テキストで構成された1つ目のサンプルスライド。共通の既定テーマ（`@slidev/theme-default`）を使用し、不要な外部依存を避けるため Web フォントは無効化されている。
   - `slides/second/slides.md`: 2つ目のサンプルスライド。1つ目と同様のテーマとフォント無効化設定を持つ。
   - `package.json`: 対象ディレクトリに存在しない場合にのみ生成する。開発依存関係（`devDependencies`）には現在のフレームワークの正確なバージョン（exact version）を記録し、`dev`, `build`, `preview` の各 npm スクリプトとして `slidock <command>` を登録する。既存のプロジェクトに対して導入する場合は既存の `package.json` を絶対に上書きせず、利用者が `npx slidock <command>` を通じて実行することを想定する。
   - `.gitignore`: 対象ディレクトリに存在しない場合にのみ生成する。
2. **ゼロ書き込み原則（事前衝突検査）**:
   展開を予定している必須ファイル（設定ファイルやスライド群）について、書き込みを開始する前に衝突検査（Preflight collision check）を実施する。既存の `package.json` や `.gitignore` は存在してもエラーとせず保持・スキップされるが、必須のスキャフォールドファイルで衝突が検知された場合は、上書きフラグや強制実行フラグ（`--force` や `--overwrite` など）は提供せず、処理を即座にエラーとして中断する。一部のファイルだけが生成されて中途半端な状態に残されることを防ぐため、衝突時にはスキャフォールドのファイル書き込みを一切行わない。
3. **副作用の排除**:
   雛形生成の処理中には、パッケージマネージャによる依存関係のインストール、Git リポジトリの自動初期化、および外部ネットワークとの通信は一切行わない。
4. **完了結果の報告**:
   生成処理が成功した際は、作成されたプロジェクトのルートパス、生成された全ファイルのリスト、および次に実行すべき操作指示（ディレクトリ移動やパッケージインストールの手順）を明確に出力する。

### 4. パッケージング、依存関係解決、ライセンス

#### 4.1 パッケージ構造と推移的依存関係の解決
利用者が Slidock を導入する際、複雑な内部構成やリポジトリ固有の構造を意識させることなく、標準的な npm エコシステムの手順で完結できる配布形態を確立する。

- **単一エントリによる自己完結**: 通常の npm 利用者環境のテストにおいては、公開パッケージである `@slidock/slidock` のみをインストールし、すべての内部依存関係が標準的な解決手順に従って自然に解決されなければならない。開発用リポジトリ内のシンボリックリンクや、ルート側のワークスペース設定、コピーされた上書き用設定などに依存した配布形態を禁ずる。これとは別に、pnpm によるプライベート tarball の検証ゲートは独立したテスト工程として維持する。
- **推移的ツールチェーンのパッケージング調査**: 推移的なツールチェーンのパッケージング検証（調査ゲート）に基づき、検証済みの標準的な依存関係解決が機能する場合はそれを優先する。ツール間の非互換性を回避するために依存関係の固定（オーバーライド）が必要となる場合は、利用者のプロジェクト側にオーバーライド設定を強いるのではなく、パッケージ自身が管理する固定配布（package-owned pinned distribution）によって解決する。
- **Slidev バージョンの適合範囲**: Slidev のあらゆるバージョンへの対応を無差別に保証するのではなく、検証済みのアダプタとして現行の `52.15.2` および `53.0.0` を明示的なサポート対象とする。

#### 4.2 ブラウザ依存の軽量化（playwright-core への移行）
スライドのサムネイル生成や静的エクスポートで用いられるヘッドレスブラウザの扱いを見直し、コアランタイムの依存関係を従来の `playwright-chromium` から `playwright-core` へと移行する。

従来のブラウザ自動化パッケージでは、インストール時に大容量の Chromium バイナリが自動的にダウンロードされ、ネットワーク帯域の消費や環境構築の遅延を招いていた。`playwright-core` を採用することにより、任意の機能であるスクリーンショット撮影機構へのインターフェースを保持しつつ、インストール時における不要な Chromium ダウンロードを排除する。なお、フレームワーク自体の開発および E2E テスト環境においては、安定したテスト実行を担保するために引き続き `playwright-chromium` を保持して検証を行う。

#### 4.3 配布成果物の品質管理とリリース手順
パッケージマニフェスト（`package.json`）の構成および契約仕様はリードエンジニアが管理・所有する。配布用 tarball の生成にあたっては、以下の品質規約を厳格に適用する。

- **必須同梱物**:
  - ルートの MIT LICENSE
  - パッケージの概要と利用手順を記した README
  - 完全な TypeScript 型定義ファイル（`.d.ts`）
  - ソースコードエクスポート
  - CLI 実行可能バイナリ（`bin`）
  - 整合性が検証された内部依存関係のバージョン番号
- **除外対象の徹底**:
  認証トークン、ローカル環境の絶対パス、デバッグ用ログ、および中間ビルド成果物は tarball 内に一切含めてはならない。
- **リリース検証フロー**:
  配布物の準備段階では、パックおよびリリースのドライランレポートを出力するスクリプトを実行し、成果物の内容を検証してアルファ版のパッケージを作成する。実際のレジストリ公開（npm publish）や Git プッシュは実装作業中には実行せず、最終的な利用者の承認に基づく独立した操作として実施する。
- **バージョン管理と公開命名規則**:
  公開パッケージ名は `@slidock/slidock` を維持する。フレームワーク内の依存関係の整合性を保つためのメタデータリリースバージョンとして `0.1.0-alpha.1` を設定可能とするが、ソースコードワークスペース内の現在のバージョン表記 `0.1.0` はリリース直前のビルド工程まで維持して差し支えない。なお、npm における対象スコープの所有権は現時点で外部検証が完了していないため、一般への即時公開が可能であると無条件に仮定してはならず、検証済みのアルファ成果物としての準備を徹底する。

## 資料管理と開発サーバー

### スライド資料の探索と収集契約
Slidockにおける資料収集処理は、指定された基底ディレクトリから複数のMarkdownファイルを検出し、共通のビルドおよび配信パイプラインへ引き渡すための入力仕様を定めます。従来の探索処理では対象ディレクトリ配下に存在するすべてのMarkdownファイルを一律に収集していましたが、大規模なプロジェクトや共同編集環境においては、特定ディレクトリの除外、公開対象の明示的な絞り込み、および安全なファイル解決が強く求められます。

この課題を解決するため、収集契約に `include` および `exclude` の各グロブ指定を追加します。これらのパターンは起点となる `sourceRoot` からの相対パスとして解釈されます。パターンの評価には、Node.js 24.15.0以上で提供されている標準APIの `path.matchesGlob` を直接使用します。これにより、外部ライブラリへの推移的な依存関係を増やすことなく、実行環境の標準機能のみで安全かつ高速にパスを判定できます。設定が省略された場合は従来の探索動作を踏襲し、既存の除外ルールを適用しながらすべてのMarkdownファイルを自動検出します。

包含と除外が重複して適用される場合は、安全性を最優先して除外ルールを常に優先（exclude wins）します。また、ファイルシステムのトラバーサル攻撃や意図しない依存関係の混入を防ぐため、`sourceRoot` の境界を越えるディレクトリ走査や、探索ルートの外部を指すシンボリックリンクの追跡は明示的に禁止します。

探索結果としてスライドが1件も検出されなかった場合、空のコレクションとして処理を継続するには `allowEmpty: true` が有効である必要があります。新設された `loadProject` を用いる新規プロジェクトの利用パスでは `allowEmpty: true` が自動的に既定値として適用されるため明示的なオプトインは不要ですが、低レベルのレガシーな設定環境では従来の既定値（`false`）がそのまま維持され、従来どおりエラーを発生させることで設定の記述誤りやパス指定の不整合による意図しない空の成果物生成を防止します。

### スライド単位の設定とメタデータの正規化
収集されたスライド資料は、プロジェクト全体の統一的な管理に加えて、資料ごとの識別子、表示順、公開状態などを個別に調整できる柔軟性を必要とします。ファイルパスに依存したままでは、ディレクトリ構造の整理に伴って公開URLが変化してしまう課題や、執筆途中の資料が意図せず公開成果物へ混入するリスクが生じます。この要件を満たすため、検出時または上書き前のスライド識別子をキーとして指定する `deckOptions` 設定を導入します。

`deckOptions` には `{id?, title?, order?, draft?, cover?}` の各項目を定義でき、自動検出されたスライドだけでなく、設定ファイル等で明示的に定義されたスライド（explicit decks）においても `title`、`order`、`draft`、`cover` の個別指定を共通してサポートします。各設定値には厳格な検証規則を適用します。
- `id`: 上書き後の識別子を指定することで、ファイルパスの変更に左右されない安定した公開URLを生成できます。ただし、複数のスライドで最終的な識別子が重複した場合は、ルーティングの競合を防ぐため即座にエラーとして処理を中断します。
- `title`: 空文字の指定は認められず、必ず内容を持つ文字列である必要があります。
- `order`: 有限数（finite number）を指定し、未指定時の既定値は `0` です。
- `draft`: 真偽値を指定し、未指定時の既定値は `false` です。`draft: true` に設定されたスライドは、コンパイル工程に入る前に開発サーバーのルーティングおよび静的ビルドの処理対象から完全に除外されます。これにより、執筆途中の資料が公開成果物や開発中のカタログへ誤って混入することを防ぎます。

スライドの表示順序は、自動検出と明示的な指定の双方において統一された順序比較器によって決定されます。比較器は `order` に指定された数値を昇順で評価し、同一の数値を持つスライド間では `id` の字句順（辞書順）で整列します。

表紙画像を指定する `cover` には、設定ディレクトリ（APIの `baseDir`）を基準とした相対パスでローカルの画像ファイル（PNG、JPEG、WebP、SVG）を指定します。ビルド時の外部通信や予期せぬネットワーク遅延を避けるため、リモートURLの取得は行いません。指定された画像は専用のコピー先パスへ配置され、公開カタログのタイトルやサムネイル表示に上書き内容が反映されます。この個別設定のためにフロントマターの許可リスト（allowlist）を拡張することは行わず、設定側で一元管理します。

設定ファイル内に、一時的に削除されたスライドや今後追加される予定のスライドに対する未知のキーが `deckOptions` に残されている場合でも、ファイルの追加や削除の途中で不必要なエラーを起こさないよう、キーの存在自体は許容されます。ただし、設定値の型が不正であるなど無効なオプション値が含まれている場合は常に拒否されます。

これらの入力値は内部表現である `NormalizedHubConfig` に統合されます。この正規化設定には、`include` や `exclude`、必要に応じた `deckOptions` やソース選択の由来情報（provenance）、サムネイル生成設定（`thumbnails: 'auto' | 'none'`）、ホーム設定、および `compatibilityGroups` や `allowEmpty` が保持されます。

新規利用パスでは既定で `compatibilityGroups: true` が有効となり、互換性調査（probing）およびプロファイルエンジンを経由してグループ化処理が行われますが、既存の低レベルなレガシー設定では従来の動作（無効）が維持されるため、従来の依存グラフ出力は変更されません。また、既存のプロファイル処理パイプラインは、互換性グループの統合処理を実行した後も、ユーザーが明示的に指定したスライドの並び順（user order）を確実に維持します。これらの一連の新しいメタデータに関しては、`draft` がコンパイル前の取り込み除外に作用し、`order` が出力カタログの並び順に、`id` が公開ルーティングURLに反映されるなど機能しますが、通信データ構造（wire shape）を変更することはなく、通信プロトコルのバージョン（wire version）引き上げや、`CatalogDeck` 型に対する新たな必須フィールドの追加は行いません。

### サムネイル生成と静的ビルド出力契約
静的ビルド処理では、各スライドのコンパイルと並行して、ポータル画面で一覧表示するためのサムネイル画像とマニフェストファイルを生成します。従来はヘッドレスブラウザによる自動撮影を既定としていましたが、CI環境やリソース制約の厳しい環境ではブラウザ起動に伴う実行負荷やプロセスの不安定化が課題となっていました。

Slidock v0.1 では、サムネイル生成の制御として `thumbnails` オプションを提供します。
- `thumbnails: 'auto'`: 従来と同様にヘッドレスブラウザを用いた自動生成を既定の挙動として実行します。撮影処理で明示的な障害が発生した場合は、原因を特定して対処できるよう実行可能なエラーとして報告します。
- `thumbnails: 'none'`: ブラウザの起動処理を完全にスキップします。この場合でも画像の欠落による表示崩れを防ぐため、PNG画像の未検出エラーを出さずに、ローカルで完結する有効なプレースホルダーSVG、カタログデータ、およびマニフェストを生成します。

個別スライドにローカルのカスタム表紙画像（`cover`）が設定されている場合は、`'auto'` と `'none'` のどちらのモードであってもその設定が有効に機能します。カスタム表紙画像を持つスライドではスクリーンショットの撮影処理がスキップされ、有効な画像パスと画像形式が維持されます。オフラインアセットの計算処理も更新され、ブラウザ起動を伴わない `'none'` モードおよびカスタム表紙画像が指定された場合の双方に対応して、必要な画像資産が正確に集計されます。

スライドが1件も存在しない空のコレクションをビルドする場合でも、`allowEmpty: true` が設定されていれば、カタログが空の状態のホームページを正常にビルドできます。この際、スライドの実行時処理や依存グラフの解析において先頭スライド（`decks[0]`）へ不用意にアクセスして例外が発生しないよう内部構造を保護し、ネイティブの空ドキュメントと互換性のある出力形状を維持します。また、スライド作成者の非公開ノート（notes）やソースファイルの物理パスが公開成果物に露出しないよう、非公開情報としての保護を徹底します。

ポータルのホームページ設定（`home`）は、既存の `HubHomeOptions` と構造的に一致する項目（`title`、`logo`、`hero`、`description`、`links`、`footer`、`categoryLabels`）を受け付けます。この設定データは、ビルド時に生成されるHTML内へデータ保持専用のスクリプトタグ `<script id="slidock-home-config" type="application/json">` として直接埋め込まれます。HTMLパーサーが途中でタグを終了してしまう事態を防ぐため、`<` などの危険な文字は安全にエスケープされます。このスクリプトタグの注入はホームページのHTMLに対してのみ行われ、各スライドのHTMLには注入されません。フロントエンドの既定ホームページはこの埋め込みデータを起動時に直接読み込むため、実行時にネットワークを介して設定ファイルを取得するリクエストは発生しません。

共有バンドルに関するレポート出力では、既存の診断情報やマニフェストから得られたグループ識別子、スライド識別子、ランタイムやテーマの種別、およびグループ化の判定理由を客観的に提示します。算出根拠のない推定削減率などを恣意的に表示することはありません。CLIのビルド結果にはグループのサマリー情報が出力されますが、公開サイトの出力データと同様に、内部のモジュールパスなどの機密情報は一切含まれません。

### 開発サーバーのライフサイクルと動的更新
ローカル開発における快適性を担保するため、開発サーバーは複数スライドの同時起動、ファイルの動的変更への即座の追従、および設定変更の反映を効率的に処理する必要があります。スライドごとに独立したプロセスを毎回再起動していては待機時間が増大し、開発体験が著しく損なわれます。

APIエントリである `devHub` は、ポート番号を任意とする従来の関数シグネチャを維持します。内部で呼び出される `startDev` は、元のオプションを再正規化する再読み込みコールバック（reload callback）と、新しいプロジェクト設定の再読み込みに使用する任意の監視パス（optional config watch path）を受け取ります。

開発サーバーの起動中にスライドファイルの追加や削除（add/unlink）が発生した場合、ファイルシステムの再走査がトリガーされます。ファイルシステムの変更検知には、既存の200msポーリング機構を維持します。この動的変更処理では、内容に変更のない既存スライドのSlidev子プロセスはそのまま維持し、新規に追加されたスライドのランタイムのみを新しく起動します。新規プロセスの準備が完了した段階で、バックエンドのプロキシルーティングとカタログデータを不可分（アトミック）に切り替え、その後に削除されたスライドの古いランタイムを安全に終了します。

ファイル走査の失敗や新規スライドの起動エラーが発生した場合でも、サーバープロセスを異常終了させることはありません。直前の正常に利用可能だったコレクションの状態を維持しながら、Viteのエラーオーバーレイをブラウザ上に表示して開発者に問題を通知します。その後、開発者によって有効な保存が行われれば、サーバーは自動的に正常な状態へと復帰します。スライドが1件も存在しない空のコレクション状態からサーバーを開始した場合でも、ホームページとカタログ画面を安定して配信し続け、後から最初のスライドが追加された時点で自動的に検知して子プロセスを立ち上げます。

画面キャプチャの処理においては、古いスクリーンショットのインデックス参照や、削除されたスライドに対するキャプチャ要求が残存していても、例外によってプロセス全体がクラッシュしないよう耐障害性を確保しています。また、既定である `thumbnails: 'none'` が選択されている開発環境では、ブラウザの起動処理そのものを省略し、軽量な開発体験を提供します。

開発サーバー内の可変プロキシルーティング（mutable proxy routing）は、HTTPリクエストおよびWebSocket通信の両方を透過的に処理します。URLエンコードされたスライド識別子を含むパスも正確に解釈し、プレフィックスが最も長いルートを優先する最長一致（longest route first）に基づいて適切なスライドの子プロセスへ転送します。定義されていない未知のルートに対しては404エラーを返却します。スライド編集時におけるページ番号を維持したホットモジュール置換（HMR）の動作も損なわれません。

ポータルのホームページ設定（`home`）が変更された場合は、接続中のフロントエンドクライアントへ通知を送り、ホームページの自動リロードを実行します。設定全体のトポロジが変更された場合は影響を受けるバックエンドプロセスのみを再起動し、通常のスライドMarkdownファイルの編集時はSlidevのランタイムを維持して高速な再描画を継続します。

サーバーのシャットダウン時には、進行中の画面リフレッシュやサムネイルキャプチャのタスクをすべて排他的に完了（drain）させた上で、起動中のヘッドレスブラウザ、すべてのスライド子プロセス、およびファイル監視ウォッチャーを整然と閉鎖します。

### プロジェクト設定連携と拡張オプション契約
開発サーバーがフレームワークの外部ツールやCLIと連携する際、シリアライズできない動的なコールバックや拡張設定を受け渡すインターフェースが求められます。しかし、コアの設定正規化処理にこうした実行時固有のオブジェクトを混入させると、設定の再現性や構造の純粋性が損なわれてしまいます。

プロジェクトCLIから `devHub` を呼び出す場合、開発環境専用の新しい任意引数として `resolveOptions` 関数を提供できます。この関数は非シリアル化可能（non-serializable）であり、呼び出し元から `HubBuildOptions` を非同期で返却します。最終的な統合において、設定ファイルが選択されている場合は `HubDevOptions.watchFiles` に読み込まれた設定パス（`loadedProject.configPath`）が渡され、`resolveOptions` がリフレッシュごとに `loadProject` を再実行して最新の設定を再取得します。

これらの開発時固有のパラメータは、設定の正規化パイプラインの外部で消費される `HubDevOptions` 型として定義されます。
- `port`: 待受ポート番号（任意）。
- `resolveOptions`: 最新の `HubBuildOptions` を非同期で取得する関数（任意）。
- `watchFiles`: 設定変更に伴って再読み込みを監視すべきファイルパスの配列（任意）。

この構成により、コアの設定正規化処理に開発専用の非シリアル化データを混入させることなく、CLIや外部統合ツールが開発サーバーのライフサイクルを安全に制御できる契約を維持します。

## Web API・実装分担・検証

### フロントエンド API

#### カタログ抽出関数 `selectCatalogDecks`
Web フロントエンドにおいて、カタログに含まれるスライドデッキの一覧から利用者が求めるデッキを検索し、並べ替えて表示する機能は不可欠である。しかし、ブラウザ上で動作する画面部品が Node.js 固有のモジュールや外部通信に依存してしまうと、実行環境が制限され、ポータブルで軽量な配信というフレームワークの目標が損なわれる。また、検索や並べ替えの処理によって入力データの配列が直接変更されると、リアクティブな状態管理において予期せぬ不整合を招く。

この課題を解決するため、Node.js への依存を排除した純粋なクライアントサイド関数として `selectCatalogDecks` を提供する。本関数は入力されたデッキ一覧を一切変更せず、常に条件を適用した新しい配列を生成して返す。
関数の型シグネチャは以下のとおりである。

```typescript
selectCatalogDecks(
  decks: readonly CatalogDeck[],
  options?: {
    query?: string;
    category?: string;
    tag?: string;
    sort?: 'catalog' | 'title' | 'date';
  }
): CatalogDeck[]
```

指定可能な絞り込み条件および並べ替えの挙動は、以下の仕様に基づいて処理される。
- 検索語句（`query`）：
  前後の空白を取り除いた上で、大文字と小文字を区別しない部分一致検索を行う。検索対象は公開情報として定義されたメタデータに限定し、タイトル（title）、説明文（description）、著者（author）、およびタグ（tags）を走査する。
- カテゴリ（`category`）：
  指定された文字列に対する完全一致、またはスラッシュ区切りのプレフィックスに基づく階層的一致（親カテゴリの指定による子孫階層の包含）を判定する。
- タグ（`tag`）：
  指定された文字列と完全に一致するタグを持つデッキのみを抽出する。
- 複合条件の統合：
  検索語句、カテゴリ、タグの各条件が複数指定された場合は、すべての条件を満たすデッキのみを抽出する AND 条件として処理する。
- 並べ替え（`sort`）：
  - `'catalog'`: 設定ファイルから渡された元の配列の順序をそのまま保持する。
  - `'title'`: タイトルの文字列に基づき、決定論的な辞書順で比較する。タイトルが同一の場合は一意の ID で比較して順序を一意に決定する。
  - `'date'`: 有効な日付文字列を降順（新しい日付が先頭）で整列する。日付が不正なものや未設定のデッキは配列の末尾に配置し、日付が同一であるデッキ同士は元の配列の出現順を保持する。

#### ホーム画面コンポーネント `SlidockHome`
フレームワークを利用する開発者が、ポータル画面を一から構築することなく利用できるようにしつつ、細かな表示制御や外部状態との同期を柔軟に行える仕組みが求められる。

このため、既存のコンポーネント構成やスロット、およびカテゴリ選択用の `v-model` を維持した上で、`SlidockHome` コンポーネントに以下のプロパティと双方向バインディングを追加する。
- 双方向バインディング（`v-model`）：
  検索語句（`v-model:query`）、タグ選択（`v-model:tag`）、および並べ替え基準（`v-model:sort`）を新設し、コンポーネント外部の状態と双方向で同期できるようにする。
- コントロール表示プロパティ（`controls`）：
  真偽値を受け取る `controls`（初期値は `true`）を提供する。既定では検索入力欄、タグセレクタ、ソートセレクタが表示され、支援技術で正しく認識できるようそれぞれにアクセシブルな名前（accessible names）を付与する。`controls` に `false` を指定すると既定のコントロール要素群は画面から除去されるが、外部の `v-model` やスロットを経由した操作機能はそのまま継続して利用できる。
- ツールバーのスロット提供：
  独自の操作 UI を配置したい利用者のために、現在の操作状態や状態更新関数（setters）を受け取れる `toolbar` スロットを任意で利用可能な形式として提供する。
- 状態の保持と結果表示の分離：
  カテゴリによる絞り込み機能は従来どおり保持され、カタログデータが外部から更新された場合でも利用者が操作中のコントロール状態は維持される。また、検索や絞り込みの結果として該当デッキが 0 件になった状態（empty result）と、そもそもカタログにデッキが 1 件も登録されていない状態（no decks）を明確に区別して画面に表示する。外観の調整は既存の Vue デザインを踏襲し、小規模な変更にとどめる。

### スタイル分離と外部統合

#### CSS のスコープ分離とホスト環境の保護
フレームワークが提供する CSS が、組み込み先ホストの全体スタイル（背景色やリンク装飾など）を意図せず上書きしてしまうと、利用側のアプリケーションとデザインの衝突が発生する。一方で、コンポーネントを単独で描画する際にも意図した表示が保たれるよう、適切なフォールバックを備える必要がある。

この課題に対処するため、スタイルシートをコンポーネント用とページ全体用に分離する。
- `/frontend/style.css`：
  コンポーネント固有のスコープ化された既定スタイルのみを収録する。対象はライブラリ、カード、カテゴリの各ルート要素に限定し、`:root`、`body`、全称セレクタ（`*`）、および修飾のない `a` や `button` といった大域セレクタを完全に排除する。これにより、既存のカスタムエントリが `style.css` を読み込んでもホスト環境の `body` やリンクに影響を与えない設計とし、テスト時には番兵スタイル（sentinel styles）を配置してホスト側のスタイルが汚染されないことを検証する。
- `/frontend/site.css`：
  既定のホーム画面および新規スキャフォールド専用の、明示的なフルページ向けリセットおよびテーマ基準線として新設する。
- 変数の互換性と単体描画：
  従来の `--hub-*` プレフィックスを持つ CSS 変数は互換性のために保持する。各コンポーネントは単体で描画された場合でも外観が崩れないよう、コンポーネント内部に自前のスタイルおよび既定の CSS 変数フォールバックを備える。

#### Vue コンポーネントのエクスポートと外部ビルド
利用側の Vite + Vue プロジェクトがコンポーネントを取り込んで利用する際、スロットの受け渡しや TypeScript の型定義が正常に動作することを保証する必要がある。ただし、初期段階で過度な事前コンパイルを課すと、開発の俊敏性や追跡性が損なわれる懸念がある。

そのため、初期リリースでは単一ファイルコンポーネントをソース形式のままエクスポートする方針を維持する。Node.js 24（Node >= 24.15.0）を動作基準とし、バージョンを固定したツールチェーン構成をドキュメントに明記して外部の Vite + Vue 環境をサポートする。ビルドおよびエクスポートの検証では、利用側でのスロット利用と型チェック（typecheck）が正しく成立することを実証する。外部統合で実際の不具合が発生しない限り、事前コンパイルの導入は行わない。

### タスク依存関係と実装分担

#### タスク依存関係グラフ
各作業領域の境界を明確にし、並行開発を阻害しない依存関係グラフを定義する。
1. 並行実装フェーズ：
   ビルド設定やメタデータ抽出を扱う管理タスク（management）と、フロントエンド API および UI を扱うフロントエンドタスク（frontend）は、互いに依存せず並行して実装を進める。
2. 統合消費フェーズ：
   プロジェクト CLI タスク（project CLI）は、管理タスクによって確定した設定コントラクトを入力として消費して実装する。
   開発ライフサイクルタスク（dev lifecycle）は、正規化された設定オブジェクトとコールバックの形式を消費して実装する。
3. 配布パッケージ統合フェーズ：
   配布タスク（distribution）は、npm パッケージの整合性検証（npm probe）が完了した後に、ビルド済みの実行バイナリとフロントエンド資産を単一エントリへと統合する。

#### 責任範囲と作業規律
- リード（Lead）の役割：
  パッケージマニフェスト（`package.json`）、ロックファイル、公開される Node.js エクスポート定義、ドキュメント、ライセンスの管理、およびタスク横断的な最終統合を一貫して担当する。
- 作業担当者（Luna workers）の規律：
  互いに重複しない、境界が明確に定められた個別タスクを担当する。割り当てられたタスクを他の担当者へ再委任することは禁止する。
- 既存 CLI の更新：
  既存の `@slidock/cli` に対するパススルー更新は、プロジェクト CLI の担当者が責任を持って維持する。これにより、フレームワークから CLI への循環依存を防止しつつ、既存の機能性を確実に維持する。なお、実装作業期間中は npm への公開、リモートへの push、外部デプロイは行わず、レビュー可能なアルファ成果物の準備にとどめる。

### 検証方針と受入基準

#### 一時環境による受入検証
新規の利用者が単一の公開エントリ `@slidock/slidock` を導入した際に、期待どおりの動作が一貫して行われるかを検証するため、一時ディレクトリ上にクリーンな利用側環境（fresh temporary consumer）を構築して以下の受入項目を検証する。
- パッケージ導入とプロジェクト生成：
  ローカルスコープのテストレジストリまたはパック依存解決（packed dependency resolution）を通じて、単一の公開エントリ `@slidock/slidock` をインストールできること。また、新規プロジェクト生成時に既存ファイルを誤って上書きしない（create without overwrite）安全策が機能していること。
- デッキ一覧と基本ライフサイクル：
  同一テーマを持つ 2 つのデッキが存在する状態で、一覧表示、ページ間のナビゲーション、および画面の再描画（refresh）が正常に行われること。また、デッキの新規追加、削除、一覧が空になる状態、およびその状態からの復元（recover）という一連の動的ライフサイクルを検証する。
- スロットとスタイルの保護：
  利用側が指定したカスタムカードスロットが正しく差し込まれること、およびホスト環境側の CSS がフレームワークのスタイルによって破壊されないことを実証する。
- 下書き除外とメタデータの安定性：
  出力生成物から下書き（draft）状態のファイルが確実に排除されていること。また、表示されるデッキの並び順が仕様どおりであり、安定した ID が各デッキに付与されていることを確認する。
- 軽量パスの動作保証：
  新たな利便性パスにおいて、Chromium の自動取得やオフライン用外部ダウンロードを行わない軽量な既定挙動（no browser default）が意図どおり成立していること。なお、従来の `buildHub` における `offline=true` や `thumbnails=auto` という既定値はそのまま維持される。
- 深階層ルーティングと配備制約の確認：
  深い階層のルーティング（deep routes）を含むビルドおよびプレビューが正常に機能すること。ただし、本バージョンで検証および保証されるのは静的なルートパス配備（root-path static deployment）のみであり、非ルートのベースパス（non-root `basePath`）の設定は明確に拒否され、未サポートの機能として誤認されないようにする。
- アセット共有とテーマの分離：
  互換性のあるデッキ間において、共通アセットが正しく共有されていることを示すレポートおよび検証結果を得ること。一方で、異なるテーマが適用されたデッキ間では、既存のテスト用フィクスチャを再利用し、相互のスタイルや設定が厳格に分離されていることを実証する。
- 外部統合と型検査：
  独立した Vite + Vue 環境において、フレームワークのコンポーネントやスロットを正しくインポートし、ビルド処理および TypeScript の型チェック（typecheck）が正常に完遂できること。

#### 検証環境の分離と実行規律
- パッケージマネージャーの個別検証：
  npm と pnpm の検証ゲートを厳格に分離し、双方のパッケージマネージャー環境で依存解決やスクリプト実行が問題なく成立することを独立して確認する。
- 実行ディレクトリの独立と疑似出力の排除：
  テスト実行時のカレントワーキングディレクトリ（cwd）は、リポジトリのチェックアウトディレクトリ外に配置して実行する。これにより、テスト側で生成したファイルをリポジトリ本体の共有出力と見せかけるような偽装（test fakes）を排除し、完全な外部利用者視点での動作を担保する。
- 統合後チェックと実ブラウザテスト：
  各タスクの統合完了後、リポジトリのルートで `pnpm check` を実行する。また、対象を絞った実ブラウザ環境での統合テスト、および実際にパックされた配布物を用いたコンシューマライフサイクルの実機検証を実施する。
- 既存ポータブル CLI の確認：
  実行が可能である場合は、既存のポータブル／パック済み CLI の適用を試行し、前提条件や依存関係が不足している場合はその内容を正確に記録・報告する。

#### 評価結果の記録と未検証事項の明確化
- 記録と成果物の保存：
  すべての検証結果は `docs/results/framework-v01.json` に構造化データとして記録し、実行ログは `artifacts/framework-v01/` ディレクトリ配下に保存する。
- 主張範囲の限定（未検証事項の不言明）：
  本バージョンにおける検証は、現時点で測定が行われている Linux 環境を基準とする。macOS や Windows 上での完全な動作、多様なバージョン間での完全な互換性、稼働中のクラウド環境（live cloud）での実行、および npm 公開レジストリからの公開インストールについては、実際の CI や実機での計測が完了するまでは動作保証として主張しない。
  また、ネイティブ層に対する新たな変更は行っておらず、既存のプロトコルを維持しているため、ネイティブ OS レベルでの受入完了を根拠なく表明することは避ける。
